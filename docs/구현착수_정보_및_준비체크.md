- 기준 문서: `모션나인_발주현황_기획설계서.md` v1.1 및 현재 저장소 소스
- 작성일: 2026-09-27
- 목적: Supabase·Google·무료 메일·Cloudflare 계정 준비와 구현 착수 순서 정리

## 1. 프로젝트 전체 구성

```text
관리자 브라우저
  ├── Cloudflare Pages Free: web/ 정적 파일 (HTML·CSS·JS·자체 호스팅 라이브러리)
  └── Supabase Free: Auth + PostgreSQL + RLS + RPC
       ├── Google OAuth
       └── Custom SMTP 무료 발신자 (보유 도메인 + Resend Free 또는 전용 Gmail 후보)

PNG·PDF: 관리자의 브라우저에서 생성해 기기에 저장
```

Cloudflare Pages에는 사용자별 발주 레코드나 비밀번호를 올리지 않는다. Supabase의 공개용 웹 키는 브라우저가 프로젝트를 식별하는 데 사용되므로 RLS가 발주·관리자 데이터를 보호해야 한다. secret/service-role 키, Google Client Secret, SMTP 비밀번호, 데이터베이스 비밀번호는 사이트 코드·문서·Git에 넣지 않는다. Supabase는 2026년 말까지 구형 `anon`·`service_role` 키 폐기를 예정하고 있어, 신규 프로젝트에서는 공개용 `sb_publishable_...` 형식 키를 준비한다. 브라우저의 공개용 publishable key는 RLS 대체재가 아니다. [Supabase API 키 보안 문서](https://supabase.com/docs/guides/getting-started/api-keys)

## 3. Supabase 무료 프로젝트 준비

### 3.1 새 프로젝트가 필요한 경우

1. [Supabase Dashboard](https://supabase.com/dashboard)에 로그인해 조직과 무료 프로젝트 현황을 확인한다. 무료 플랜은 현재 활성 프로젝트 두 개 제한 및 활동이 낮은 경우 7일 후 자동 중지 조건을 고려한다.
2. 새 프로젝트는 발주관리 업무에 전용으로 만든다. 이름 예: `motionnine-orders-demo`.
3. 실제 관리자 사용자가 가장 빠르게 접속하는 리전을 대시보드에 표시된 목록에서 비교하여 정한다. DB 리전은 생성 후 변경하기 어려우므로 배포 전 지역을 정한다.
4. DB 관리자 비밀번호를 독립된 강한 비밀번호로 생성해 비밀번호 관리자에 저장한다.
5. 프로젝트 생성 후 Connect에서 Project URL·Publishable key를 가져온다. 기존 프로젝트에 Supabase 참조·테이블·데이터가 이미 있을 수 있으므로 새로 만들기 전에 상태를 확인한다.
6. 신규 설치는 `supabase/migrations/20260927000000_motion9_init.sql` 전체를 SQL Editor에서 실행한다. 조각 실행은 하지 않는다.
7. 최초 owner는 Google 또는 확인된 이메일로 가입해 Auth UUID가 생긴 다음, Dashboard → Authentication → Users에서 UUID를 복사하고 SQL Editor에서 실행한다. 예: `select * from public.motion9_bootstrap_owner('<AUTH-UUID>', '대표관리자');`. UUID를 확인하지 않고 임의 주소로 실행하지 않는다.
8. 기획서의 검증용 SQL 결과가 맞는지 확인한 뒤 Auth·Cloudflare를 연결한다. DB 검증에 실패하면 이후 관리자 계정을 승인하지 않는다.

SQL Editor에서 실제 실행할 파일은 저장소의 마이그레이션 주석 순서를 따른다. 신규 프로젝트 기준은 1회만 실행하며, 주문자 추가 마이그레이션 재적용 여부는 `docs/구현지시서/README.md`와 `AGENTS.md` 기준을 따른다. Free DB에는 유료 백업 보장이 있다고 가정하지 않는다.

### 3.2 화면 설정값과 비밀의 구분

현재 브라우저 클라이언트 코드는 다음 세 값을 `web/js/config.local.js`에서 읽는다.

| 현재 속성명 | 공급자 화면에서 가져올 값 | 웹 번들 공개 여부 |
|---|---|---|
| `SUPABASE_URL` | Supabase Project URL (`https://<project-ref>.supabase.co`) | 공개 가능 |
| `SUPABASE_ANON_KEY` | 신규 프로젝트의 Publishable key (`sb_publishable_...`) | 공개 가능, RLS 필수 |
| `SITE_URL` | 실제 Cloudflare Pages 공개 기본 주소 | 공개 가능 |
| `ENV` | 배포 구분용 `prod` 또는 시연 환경 이름 | 공개 가능 |

`SUPABASE_ANON_KEY`는 현재 코드 호환용 속성 이름이며, **이 필드 값은 화면에 공개해도 되는 publishable key로 제한한다.** `sb_secret_...`, 과거의 `service_role`, 데이터베이스 비밀번호, Google Client Secret, SMTP 앱 비밀번호를 대입하지 않는다. 프로젝트에는 `.gitignore` 처리된 `web/js/config.local.js`가 이미 있을 수 있다. 파일 내용은 메시지·분석 출력에 붙이지 말고, 이 체크리스트에는 계정 비밀값을 채우지 않는다. 값 노출이 의심되면 각 공급자 대시보드에서 해당 키를 교체하고 세션을 확인한다.

현재 예제 파일: [`web/js/config.local.example.js`](../web/js/config.local.example.js)

## 4. Google 로그인 준비

### 4.1 Google Cloud Console

1. [Google Cloud Console](https://console.cloud.google.com/)에서 모션나인용 Google Cloud 프로젝트를 선택한다.
2. Google Auth Platform에서 앱 이름·지원 이메일·연락처를 설정하고 OAuth consent screen의 Audience/Test users에 시연 관리자 계정을 추가한다.
3. Credentials에서 OAuth Client ID → Web application을 생성한다.
4. **Authorized redirect URI**에 아래 Supabase 주소를 등록한다. `project-ref`는 Supabase URL의 실제 고유 project ref로 치환한다.

```text
https://<project-ref>.supabase.co/auth/v1/callback
```

Google OAuth Client ID와 Client Secret을 다운로드·복사한다. Secret은 Supabase 대시보드의 Google provider 설정으로만 전달한다. Google 설정 가이드는 [Supabase Google Auth 안내](https://supabase.com/docs/guides/auth/social-login/auth-google)를 따른다.

### 4.2 Supabase Auth

1. Authentication → Sign In / Providers → Google을 켠다.
2. Google Cloud의 Client ID·Client Secret을 해당 항목에 입력한다.
3. Provider의 Callback URL 표기가 위 URI와 정확히 일치하는지 확인한다.
4. Confirm email을 이메일 가입에 활성화한다. provider별 계정이 같은 사람이라고 이메일 문자열만 보고 자동 합치지 않는다.
5. 등록한 시연용 Pages 주소·`/html/callback.html`만 redirect allowlist에 추가한다.
6. Code exchange·성공·거절·OAuth 취소를 확인한다. Google 사용자도 `pending` 승인 흐름을 거친다.

## 5. 이메일 인증을 무료 범위에서 준비

Supabase 기본 SMTP는 실제 공개 관리자에게 편지를 보내는 서비스로 쓰지 않는다. 외부 메일 주소는 거절되거나 낮은 발송 한도에 걸릴 수 있다. 다음 순서로 무료 발송 수단을 고르고 인증 메일을 실제 주소로 수신 확인한다. Supabase도 일반 가입 사용자의 이메일 전송에는 custom SMTP를 권장한다. [Supabase SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)

| 확인 항목 | 조직의 발송 도메인 보유 | 도메인 없음 |
|---|---|---|
| 1차 후보 | Resend Free; 기존 보유 도메인만 DNS 검증 | 전용 무료 Gmail SMTP 후보 |
| 비용 원칙 | Free plan 안에서만 발송 | 계정·SMTP가 무료일 때만 채택 |
| Supabase 경로 | Authentication → SMTP Settings → custom SMTP 입력 | 동일한 custom SMTP 입력 |
| 서버 인증정보 위치 | Resend SMTP credentials 및 대시보드에만 저장 | Google 앱 비밀번호와 Supabase Dashboard에만 저장 |
| 사전 확인 | SPF/DKIM(서비스가 안내한 DNS 레코드) 적용·verified 상태 | 2단계 인증, 앱 비밀번호 허용 여부, TLS 로그인 확인 |
| 운영 범위 | 인증·재설정 위주, 3,000건/월·100건/일 free quota 범위 | 관리자 3~5명의 낮은 인증·재설정 트래픽만 시험 |

Resend를 사용하려면 소유 도메인을 등록·검증해야 한다. 도메인이 없다면 도메인을 구입해 0원 유지 조건을 깨지 않는다. Gmail SMTP는 고정적인 전송 서비스 SLA로 보지 않는다. App Password 기능이 계정에 표시되지 않거나 관리자 정책이 SMTP를 막으면 이 경로는 실패다. 이 경우 Google 로그인으로 핵심 시연을 이어가고 이메일 인증은 해결 전까지 미완료로 기록한다. 무료 메일 한도 초과는 유료 전환으로 자동 해결하지 않는다. [Resend Free 가격](https://resend.com/pricing), [Resend 도메인 조건](https://resend.com/docs/dashboard/domains/introduction), [Google 앱 비밀번호 조건](https://support.google.com/accounts/answer/185833?hl=en), [Gmail SMTP 설정](https://support.google.com/mail/answer/7104828?hl=en)

### 5.1 이메일 링크와 리디렉션

현재 소스는 확인·비밀번호 재설정·Google 인증에서 아래 상대 페이지로 복귀하도록 구현되어 있다.

```text
Cloudflare 기본 주소: https://<project>.pages.dev
Supabase Site URL:    https://<project>.pages.dev
Allowed callback URL: https://<project>.pages.dev/html/callback.html
비밀번호 재설정:       https://<project>.pages.dev/html/callback.html?type=recovery
Google → Supabase:    https://<project-ref>.supabase.co/auth/v1/callback
```

Site URL에는 기본 사이트 origin을 입력하고, redirect allowlist에는 실제로 쓰는 callback URL을 등록한다. Supabase와 Google의 redirect URL 역할은 다르므로 혼동하지 않는다. 이메일 템플릿의 본문 링크가 Cloudflare의 callback으로 돌아오는지 테스트한다. callback이나 reset URL을 사용자에게 공개하기 전 [Supabase Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls)를 확인한다.

## 6. Cloudflare Pages Free 배포 정보

1. [Cloudflare Dashboard](https://dash.cloudflare.com/) → Workers & Pages → Create → Pages에서 기존 프로젝트·연결 저장소를 먼저 확인한다.
2. 현재 Git remote `origin`은 `https://github.com/smjjang-dev/motionnine`이고 `main`이 `origin/main`을 추적한다. Cloudflare에서 Git 연동으로 배포한다면 이 저장소와 `main` branch가 실제 Pages 프로젝트에 연결돼 있는지 Dashboard에서 확인한다. Git remote 설정이 곧 Cloudflare 자동 배포 연결을 의미하지는 않는다.
3. Build command를 비워 두고 Build output directory에 `web`을 지정한다. 프레임워크 프리셋이 필요한 빌드를 실행하지 않는다. `web/`에 `_headers`, `html/`, `css/`, `js/`, `img/`, `vendor/`가 들어 있는지 확인한다.
4. 프로젝트 생성 시 받는 `https://<project>.pages.dev` 주소를 기록한다. 자체 도메인을 새로 구매하지 않는다.
5. `web/js/config.local.js`를 깃 저장소에 포함하는 설정은 사용하지 않는다. 민감하지 않은 publishable URL/key만 현재 정적 소스 구성을 따르는 안전한 배포 주입 방법으로 준비한다. 실제 서비스 키가 없어도 브라우저 전용 publishable key 자체는 안전하게 공개될 수 있으나, Secret key는 어떠한 번들에도 포함하지 않는다.
6. **시연 URL이 바뀌면** `SITE_URL`, Supabase Site URL, callback allowlist를 함께 바꾼다. Preview 브랜치 URL이 임시로 생겨도 그대로 영구 allowlist에 두지 않는다.
7. 배포 뒤 시크릿이 HTML/JS 응답·소스 map·저장소에 없는지 확인하고 `web/_headers`의 CSP·`noindex` 헤더가 실제 배포에 적용되는지 검사한다.
8. CF에 빌드 배포될 뿐 정적 Pages 자체에서 DB 자동 백업, 메일 발신, 사용자 데이터 권한 검사가 제공되지는 않는다. 권한·기록은 Supabase DB에서 강제한다.

현재 HTML·JS는 `config.local.js` 형태의 로컬 설정을 ES module로 동적 import한다. Pages의 정적 output 디렉터리는 Pages 환경변수를 실행 시 HTML에 자동으로 읽어들이지 않는다. 따라서 신규 배포 주소를 잡은 후 공개 URL·publishable key를 정적 소스에 빌드 타임에 안전하게 주입하거나 페이지에 공개 설정 JSON을 배포하는 작은 구현 결정을 해야 한다. 이 지점을 해결하지 않으면 Pages 배포 후에도 빈 설정 자리 때문에 실제 로그인과 DB 통신이 되지 않는다. 해결 방법을 바꿔도 Supabase secret/SMTP/Google Secret을 웹으로 주입해서는 안 된다.

Free 플랜 페이지 요청 제한과 파일 제한은 **정적 웹사이트 배포 규칙**이다. 버튼·폼이 외형상 보인다는 것과 Supabase Auth/DB가 바인딩되었다는 것은 다르다. 다음에 반드시 DB 연결·로그인을 확인한다. 공식 한도는 [Cloudflare Pages 제한](https://developers.cloudflare.com/pages/platform/limits/)과 [Pages 가격·Functions](https://developers.cloudflare.com/pages/functions/pricing/)에서 확인한다.

## 8. 구현 전 업무·개인정보 결정

기존 사용자 요구사항에는 주문자 정보를 포함시키지 않았지만 현재 구현과 DB에서는 아래 값이 존재한다.

| 기존 구현 데이터 | 필수 수준 | 확인할 내용 |
|---|---|---|
| 주문자 이름 `orderer_name` | 필수 | 발주 등록 때 별도 주문자 실명이 필요한 업무인지 |
| 주문자 연락처 `orderer_phone` | 필수 | 개인 휴대폰을 수집·보관해야 하는 이유와 보관 기간 |
| 주문자 이메일 `orderer_email` | 선택 | 알림 목적이 있는지, 계정 이메일과 혼동하지 않는지 |

주문자 이름·연락처는 발주 거래처명과 다른 개인 데이터다. 실제 업무상 필요가 확인되면 사용 목적, 접근 범위, 삭제·보관 기간을 정한다. 필요 없으면 구현자는 마이그레이션·폼·검색·명세서·검증 체크리스트에서 해당 컬럼을 함께 빼고, 이미 DB가 구축됐다면 보존 필요성 확인 후 별도 마이그레이션을 작성한다. 저장된 마이그레이션 파일을 과거에 되돌리거나 활성 운영 DB를 독단적으로 파괴적으로 변경하지 않는다.

추가로 개발 전에 `docs/구현지시서/README.md`의 7가지 미결정 업무 규칙(단가, 배송비 포함 의미, 발주 품목 수, 관리자 수·최초 owner, 번호 날짜 기준, 무료 SMTP 수단, MOQ·삭제·반올림·단계 규칙)을 최종 결정한다.

## 9. 배포 전 진행 순서

```text
[ ] 기존 Supabase·Cloudflare 프로젝트 및 사용 URL 존재 여부 확인
[ ] 주문자 이름/연락처 필드의 업무 필요·보관기간 확정
[ ] 단가·배송비·MOQ·정원·owner·번호 규칙 최종 확정
[ ] Supabase URL / publishable key 검증 (secret은 사용하지 않음)
[ ] DB 초기 SQL 적용 여부 및 테이블·RPC·RLS 결과 확인
[ ] Google OAuth consent screen과 callback 등록
[ ] 무료 SMTP 실제 발송·수신 확인 (실패 시 이메일 가입 미완료 기록)
[ ] Pages 정적 web/ output 및 Pages HTTPS URL 확보
[ ] 런타임 공개 설정 주입 문제 해결, Secret 미노출 확인
[ ] Pages URL ↔ Supabase Site URL/allowlist ↔ Google/메일 링크 연결
[ ] Auth 사용자 가입 → 첫 owner SQL → 나머지 관리자 승인
[ ] 데이터 연결 확인 후 PC/모바일 등록·검색·수정·삭제·복원·출력 검증
```

체크리스트 완료 전 페이지가 화면에 보이더라도 “운영 시연 완료”로 판정하지 않는다.
